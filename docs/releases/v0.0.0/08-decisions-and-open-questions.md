# 08 · 决策记录与开放问题

本页区分：**讨论已经形成的共同设计前提**、**助手提出但尚未经验证的方案**、**仍未决策的选择**。初始讨论不能当作已通过的最终 PRD 或实施规范。

## A. 已收敛的目标和边界

| ID | 决策 / 共识 |
|---|---|
| D-001 | MileSprint 名称暂定，目标环境为单机、单个项目，以一个 Milestone 作为 Sprint 单元。 |
| D-002 | Issue 是最小逻辑事务，可为未完全澄清的 Feature 或未查明根因的 Bugfix。 |
| D-003 | Issue 的已知与潜在关系动态维护，包括依赖、影响、关联及冲突。 |
| D-004 | 用户可见 Issue 状态采用“待用户澄清、待实施、实施中、阻塞、关闭/取消”。 |
| D-005 | 所有范围内 Issue 达终态后进行版本集成 R1；发现问题回流形成 R2...；最终提交人工验收；用户反馈继续循环。 |
| D-006 | 核心分为 Issue Scheduler、Resource Manager、Scheduling Optimizer 三大模块。 |
| D-007 | Resource Registry 至少要能够登记模拟器、真机的版本、适测范围、数据安全等级、占用与锁。 |
| D-008 | 优化器以尽可能短的整个 Milestone 交付时间为目标，不照搬用户已填 Issue 的顺序或优先级。 |
| D-009 | 预估任务复杂度/耗时，并采集真实耗时；偏差会引起必要的计划重新计算和调整。 |
| D-010 | 尽量将人类注意力瓶颈缩小为必要澄清、外部事实与授权、最终验收等人类不可替代环节。 |

## B. 当前推荐设计（候选，尚需验证）

| ID | 候选选择 | 理由 |
|---|---|---|
| P-001 | 使用 Action 作为资源与调度最小粒度 | 避免 Issue 生命周期过长，导致编译/测试设备被无意义锁定 |
| P-002 | 资源请求采用原子组合申请 + Lease + fencing + 故障隔离 | 在动态资源需求下比简单布尔锁更可靠 |
| P-003 | 内部有独立持久 Runtime / Controller | 不依赖单个 LLM 上下文存活，便于调度和恢复 |
| P-004 | 采用滚动时域优化及事件驱动重算 | 动态依赖与耗时估计无法通过一次静态计划处理 |
| P-005 | 使用概率/区间耗时而非单点估计 | Bug 根因、资源速度存在不确定性 |
| P-006 | 资源约束关键路径 + 可行排程 + 抗抖动重排 | 避免 Ready-First 抢占关键设备，避免计划频繁震荡 |
| P-007 | 代码快照/验证结果建立可失效证据链 | 防止 Issue 局部 Closed 后因集成改动出现假阳性完成 |
| P-008 | 单写入 Worker 先验证闭环，再做受控并发 | 将调度收益和并行返工风险区分开 |
| P-009 | 以模拟实验先验证调度算法，再接入 Agent | 排除 Agent 能力波动对排程实验结论的干扰 |

## C. 开放问题

1. **最终交付形态**：纯 Skill、MCP、CLI/TUI、独立本地 Runtime 或组合？独立 Runtime 是当前倾向，但未定案。
2. **Issue 外部同步**：以 GitHub Issues/Linear 为权威，还是有本地独立 Graph 再进行映射同步？
3. **Action 的自动拆分边界**：何种工作需分解为多个 Action？谁有权合并或撤销已规划但未启动的 Action？
4. **调度算法**：启发式、CP-SAT 或混合策略；求解预算、问题规模和最优性差距目标怎样设定？
5. **耗时估计**：缺少历史样本时采用哪些代理特征？怎样校准长尾 Bugfix 和不同设备？
6. **隐性依赖推理**：如何评估置信度、调查价值和错误关系导致的串行化损失？
7. **资源安全模型**：数据安全等级是否预置，还是必须由用户自定义？如何在不同测试设备自动清理？
8. **锁与不可取消任务**：非幂等真机操作、设备断连、过期进程继续运行时，采取什么恢复策略？
9. **代码冲突/集成**：隔离工作区策略和分支权限如何对接不同仓库；共享数据库和测试 Fixture 如何处理？
10. **范围控制**：新发现的历史问题、严重回归、用户新需求如何影响本次 Milestone？
11. **真实收益证明**：怎样选取具有代表性的单机项目，排除 Agent 能力、模型成本和环境差异？
12. **资源优化目标的取舍**：除最短交付时间之外，是否设置明确成本预算、风险容忍和能耗边界？

## D. 讨论中需要保持的反对意见

- Agent 不是实际无限资源，推理限流和成本也会约束；只是相对更容易弹性扩容。
- 最大化每个资源利用率可能反而让整个 Milestone 更晚完成。
- 资源安全与避免死锁并不自动产生最优排程，它们必须与全局优化器分工。
- 传统银行家算法通常需要已知最大需求，而未知 Bug 的资源需求会动态变化。
- 每次事件都可重评估计划，但不是每次小偏差都应取消/迁移正在运行的工作。
- 现有产品是否有某种能力必须核查实际实现，不能把“没有公开宣传”等同于“没有能力”。
- Milestone 通过 R1 还不等于用户 Accepted；不可为优化时间跳过用户验收。

## E. 下一步建议

优先拟定一份可执行的 `SchedulePlan` 契约和“3 台模拟器 + 2 台真机”模拟资源池，再针对 10–20 个 Action 搭建最小可重复的 Baseline A/B/C 比较。只有完成测量后，才讨论“是否必须重写 Orchestrator”的工程投入。
