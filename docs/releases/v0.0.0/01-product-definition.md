# 01 · 产品定义、目标与边界

## 1. 问题定义

单人开发者在单机、单个代码项目中冲刺一个版本 Milestone 时，会遇到：

- 人类注意力无法高频跟踪所有 Issue 与 Agent Session，产生派发、澄清、跟进等待。
- Issue 之间存在明确或隐性的单向/双向影响、硬依赖、共享文件或数据库冲突，人工难以持续理解完整关系。
- 多 Agent 可能同时要求编译、测试、模拟器、真机或其他共享环境；简单并发造成抢占、冲突、闲置与返工。
- 大多数调度器优先执行 Ready 或高人工优先级的 Issue，却没有针对完整版本的最短交付时间做全局决策。
- 预估耗时与真实耗时持续偏离，静态计划容易过时。

## 2. MileSprint 的目标

在**用户明确的版本范围、验收标准、权限、安全与质量约束**下，最小化整个 Milestone **从启动到最终人工验收通过**的 wall-clock time：

\[
\min_{\pi}\;\mathbb E[T_{\mathrm{accepted}}(\pi)]
\]

其中 \(\pi\) 是随新的 Issue、依赖、资源状态和遥测变化而调整的调度策略。现实中无需承诺数学上的全局最优；必须能在给定时间和信息下持续提出安全、可执行、优于基准策略的计划。

### 三种不同的优化对象

| 对象 | 所代表的单位 | 是否是总体目标 |
|---|---|---|
| Milestone | 一个待交付和验收的版本范围 | **是** |
| Issue | feat/bugfix 等最小逻辑事务 | 否，不最大化关闭数量 |
| Action | 调查、编写、构建、测试、集成等最小执行调度单位 | 否，是资源规划粒度 |

**关键反直觉能力**：在资源稀缺或下游关键路径受到影响时，Optimizer 可以将已 Ready 的非关键 Action 推迟，甚至暂时让资源空闲，以便总体版本更早完成。资源利用率或 Agent 利用率并不等价于最短交付时间。

## 3. 范围与假设

- **一个开发主机 / 一个项目 / 一个 Milestone Sprint**；项目可拥有多个 Issue 和多类测试设备。远程设备能否注册仍需明确，但不改变单机控制平面的第一阶段定位。
- **Agent 是相对弹性的执行能力**，但并非物理无限：仍受模型限额、成本、上下文、并发写入冲突限制。
- Issue 创建时可能信息不全：Feature 可能未澄清，Bug 可能尚未定位；相关关系可能未知。
- 验收范围固定为用户批准的 Acceptance Contract；发现不相关历史缺陷不自动无限扩大本次冲刺。
- 人类只介入机器无法可靠替代的产品语义、外部事实、授权、冲突决策和最终人工验收。

## 4. 非目标（至少概念阶段）

- 做第二个通用 Issue Tracker、替代 GitHub Issues 或 Linear 全部产品功能。
- 为了并发率而无限开启 Agent；没有测量依据不假设并发写代码一定提高速度。
- 允许优化器自动修改业务范围、降低验收标准、忽略测试安全等级。
- 承诺准确预测所有 Bugfix 耗时，或在未知依赖和随机执行时间下保证全局最优。
- 首期建设跨机器、跨项目的分布式调度服务。

## 5. 成功指标

**主要 KPI**：Milestone Lead Time（启动至 Accepted 的时间，包含等待人工验收的实际时钟时间；可另拆分不可控等待）。

**辅助指标**：

- Resource-constrained critical-path remaining（资源约束关键路径估计剩余时间）。
- Action 排队时间、Setup/Execution/Cleanup 占用时间、设备与构建资源冲突次数。
- Human intervention count、Human wait time（必要澄清与不必要协调分别记录）。
- Rework time、合并/集成失败率、重新打开的 Issue 数量。
- 估时校准误差（按 Action 类型和资源环境分组）、计划切换开销。
- Agent 成本、构建开销及可用资源实际负载（均为辅助约束，而非优先取代质量）。

## 6. 与常见 Orchestrator 的区别（设计命题，不是性能事实）

传统自动派发核心问题是“谁已经 Ready → 交给哪个 Worker”；MileSprint 的核心问题是“根据整个版本的剩余工作和未来资源争用，**什么任务现在值得运行**”。前者可成为执行底座，后者是计划优化逻辑。

此区别尚需在受控模拟和真实项目对照中验证实际收益；不能据此宣称现有产品必然没有类似实现。
