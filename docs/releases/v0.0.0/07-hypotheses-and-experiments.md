# 07 · 核心假设、实验路线与衡量方法

> 此处是**准备验证的实验方案**。截至概念文档建立时，没有 MileSprint 实现，也不存在 MileSprint 的真实加速测试结论。

## 1. 必须拆开验证的两类问题

**调度层是否更优？** 在给定工作图、耗时分布、资源能力和容量的条件下，资源约束优化是否比优先级派发、空闲即派发更快完成整个版本？

**Agent 是否能为调度层提供足够可靠的信息？** 未知依赖、Bug 根因、资源需求、耗时估计和测试有效性是否能持续从实际执行中被正确发现与校准？

建议先用**不依赖 Coding Agent 的模拟器**回答第一个问题，再增加真实 Harness 与动态 Issue Discovery，防止调度算法与 Agent 推理能力相互混淆。

## 2. 对照策略

| 基线 | 策略 |
|---|---|
| A — Priority / Ready First | 在依赖可满足时，优先按人工优先级/创建时间派发 |
| B — Resource-aware Greedy | 排除安全不可行资源，资源一有空位就安排 Ready Action |
| C — MileSprint | 资源受限关键路径 + 耗时预测 + 预约 + 滚动重优化 |

三组比较必须在**相同 Milestone、资源容量、质量门禁、实际随机耗时样本、重复运行种子**下进行，不能通过 C 跳过测试来获得表面优势。

## 3. 具体实验场景

| 编号 | 场景 | 通过判定 |
|---|---|---|
| E1 隐性依赖 | 两个看似独立的 Issue 共享数据模型 | 发现、证据化关联，按影响改变并发策略 |
| E2 人类等待 | Issue 仍需用户回答，但可以独立调查 | 不中断其他 Action，合并最小必要提问 |
| E3 稀缺设备 | 3 台模拟器、2 台真机，不同版本和安全等级 | 匹配正确设备，不双重占用、不违规使用数据；崩溃后安全恢复 |
| E4 验证失效 | 已通过测试的 Issue 被下游变更影响 | 自动找出需重跑的验证，避免无依据沿用旧证据 |
| E5 验收回流 | R1 失败、R2 通过、人工验收追加 Bug | 新 Issue 回流并重新收敛，能最终交给用户批准 |
| E6 估时偏差 | 预计测试 20 分钟、实际 3 分钟 | 资源提前释放，必要时更新剩余关键路径；不因小偏差剧烈抖动 |
| E7 资源争用 | VM 独立但宿主 CPU/RAM 不足 | 不因逻辑资源同时空闲而造成宿主超量分配 |
| E8 计划稳定性 | 多项任务完成时间仅有小幅波动 | 重排收益必须大于切换成本，不频繁撤销运行任务 |

## 4. 建议的数据集和实验变量

- 问题规模：10、20、50、100 个 Action 的工作图。
- 依赖密度：稀疏 / 中等 / 高依赖，含潜在未确认关系。
- 资源形态：独占设备、共享 RAM/CPU、替代设备、Setup/Cleanup、资源故障。
- 预测质量：完美预估、系统性偏差、随机长尾及资源专属差异。
- 验证反馈：无回归、小比例新 Bug、多轮 Rn 循环。
- 人工响应延迟：即时、数小时及不确定时间；不可把人工验收时间“假设为零”来造出加速收益。

## 5. 统计与指标

主要指标 `T_accepted` 以及分布（中位数、p90、失败比例），同时记录：

- 最短可行排程下界或最优已知基准的差距（适用时）。
- 资源等待与空闲时间、调度器自身计算时间。
- 资源冲突、租约错误、设备数据安全违规（目标必须为零）。
- 返工、集成回归、无效测试重跑、验收反复次数。
- 人工干预次数、必要人工等待时间、Agent/API 成本。
- 预测区间校准（p50/p90 的覆盖率）、重排次数和切换损耗。

**反例也要保留**：当 Issue 完全独立、资源充裕时，复杂优化器可能没有收益，甚至因调度开销而变慢。MileSprint 需要识别何时退回廉价 Greedy 策略。

## 6. MVP 分阶段

1. **模拟排程内核**：确定性的 Work/Resource 数据模型，先比较 Greedy 与滚动优化器。
2. **真实单机资源注册与安全租约**：接入模拟器、真机、构建资源，并测量耗时。
3. **Issue Graph + 单执行 Worker 闭环**：验证自主推进、回归和人工澄清，而不是一开始就多写入 Agent。
4. **动态优化与受控多 Worker**：新增依赖发现、重排、验证证据失效、选择性并行。
5. **Harness/入口扩展**：评估 Skill、MCP、CLI/TUI 的实际摩擦与恢复表现。

## 7. 相关产品与研究线索（待专项审计）

下列仅记录讨论过的相关方向，**不构成对其缺失某能力的最终结论**：

- [Gas Town](https://github.com/gastownhall/gastown)：Worker 编排、集成队列与恢复机制。
- [Beads](https://github.com/gastownhall/beads)：Issue 持久化及依赖就绪计算。
- [OpenAI Symphony](https://github.com/openai/symphony)：围绕 Issue Tracker 的常驻 Agent 调度。
- [Google OR-Tools](https://developers.google.com/optimization)：RCPSP、CP-SAT 约束排程工具候选。
- Factory Missions、Augment Intent 等：版本/计划/验证闭环的产品参照。

正式竞品结论应以具体版本、源码或官方文档及 E1–E8 测试证据支持，而不只依赖产品介绍。MileSprint 的假定差异化是**资源约束版本级最短交付 + 动态关系推断 + 实测反馈驱动的在线重排**，仍须验证。
